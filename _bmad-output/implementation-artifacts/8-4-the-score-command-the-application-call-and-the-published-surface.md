## Intent

**Problem:** `score` has no `application/` orchestration entry and no CLI command. VFR-8 makes a capability reachable through one surface and not the other a defect, and today `score` is reachable through neither: the CLI's dispatch silently seals for any command it doesn't name, exit codes are recomputed rather than read off the ladder, and README/docs still say scoring ships later. Two digest-verification obligations prior stories routed here (`private-artifact-manifest`'s per-entry digest check, and `SealedRunRecord.isolationManifestArtifact`'s private-branch digest check) also have no caller yet, because both need `CorpusPort.resolve`, an async method AD-34 confines to `application/`.

**Approach:** Add `src/application/score.ts` as the one orchestration call chaining `ingest` → `score` → `emit`, awaiting `CorpusPort` for the two owed digest checks; wire `Command`'s fourth member through the CLI's exhaustive records and its dispatch; read the exit code and `--strict` promotion off `LadderResolution` instead of recomputing them; correct every doc sentence that still says scoring is unreachable.

## Boundaries & Constraints

**Always:** `src/application/score.ts` holds orchestration only — no validation, scoring, or policy logic (AD-14). `Command` gains `'score'` in the same five compiler-checked exhaustive records existing commands use (`INPUT_KEYS`, `TAKES_STRICT_INPUTS`, `TAKES_RUN_ID`, `EMITTED`, `COMMAND_USAGE`), plus the two the compiler does not check (`COMMANDS` at `arguments.ts:27`, the `USAGE` synopsis at `run.ts:94-102`) in the same diff. The CLI dispatch (`run.ts:262-277`, today an `if (command === 'preflight')` branch plus a `compile`/else-`seal` ternary) gains an explicit `score` branch rather than falling through anyone's `else`. `CommandOutcome`'s existing `'verdict'` kind (`exit-codes.ts:20-27`) is `score`'s outcome; `exitCodeFor`/`verdictExit` read `LadderResolution.exitCode` and `.strictPromotable` directly rather than recomputing FAIL/CONCERNS logic or carrying an independently-computed `evidenceConditionsOnly`. The artifact goes to `<target>/evidence-artifact.json` via the existing `emitArtifact`/`outputPath` convention. `docs/ad21-verdict-decision.generated.md` gains an exit-code column sourced from `LADDER_EXIT_CODES` (`ladder.ts:214-220`), regenerated via `generate:ad21-table` with `check:ad21-table` green. Every corrected doc sentence stays accurate the instant this diff lands (Story 8.3's Round 1 finding: don't narrow a false claim, remove it).

**Ask First:** none — ambiguities below are settled by construction per standing instruction.

**Never:** `score.ts` does not re-implement `ingest`/`score`/`emit`'s logic, only calls them. The command does not reach any capability the library itself cannot (AD-14). Public-storage `ArtifactReference` branches are out of scope for the new port-awaiting digest wiring: `CorpusPort.resolve` takes a `privateRef` and has no public-file counterpart, and nothing in the package reads `ArtifactReference.path` today, so the public branch has neither a port to await nor an existing byte-read to reuse (Decision 3).

**Acceptance Criteria:**
- Given a full valid chain of inputs, when `eval-quality score` runs, then it writes `evidence-artifact.json` and exits with `LadderResolution.exitCode`, promoted through `--strict` only via `LadderResolution.strictPromotable`.
- Given `src/cli/run.ts`'s dispatch, when an unrecognized command reaches it, then it returns a usage error rather than silently sealing.
- Given `npm run check:ad21-table`, when it runs after `generate:ad21-table`, then it is green with the new exit-code column populated from `LADDER_EXIT_CODES`.
- Given `npm run check:doc-invocations`, when it runs against the built binary, then every newly documented `score` invocation succeeds.
- Given `npm run validate`, when it runs, then it exits 0 with `src/core/**` at or above 90/90 and `check:boundary`/`check:lineage`/`check:layers` green.
- Given a ladder resolution on the Invalid rung, when `score` runs, then the command exits 3 and `--strict` promotes nothing, with no `Verdict` value invented to stand in for the resolution's `null`.
- Given a `--private-manifest` entry or a private-storage `isolationManifestArtifact` whose resolved bytes disagree with its declared digest, when `score` runs, then the run invalidates via the existing `digest-mismatch` fault path rather than silently passing.

## Decisions settled by construction

**Decision 1: kept as one spec despite exceeding the 900-1600 token guideline.** The command has no orchestration entry to test until `ingest`/`score`/`emit` are wired together in one call, and the two owed digest checks need the same async port-awaiting entry point AD-34 confines to `application/` — splitting the command surface from the digest wiring would ship a `score` command that ignores two artifact references it receives, or ship an uncalled async comparator a second time. Same reasoning as Story 8.2's Decision 7 and Story 8.3's Decision 10: the ceiling is a proposal, not a gate.

**Decision 2: `docs/explanation/roadmap.md`'s own text is corrected for consistency, even though epics.md misattributed the AC's target sentence.** The literal "no command and no library call computes contract strength" sentence lives in `docs/index.md:78`, not `roadmap.md`; `docs/explanation/behavioral-evaluation-contracts.md:163` carries a same-shape sibling. All three are corrected, following Story 8.3's Decision 9 precedent for a misattributed epics.md citation: the technical fact is recorded and acted on rather than the imprecise citation followed literally.

**Decision 3: the new port-awaiting digest wiring covers only the `private` branch of `ArtifactReference`.** `CorpusPort.resolve` takes a `privateRef` and has no public-file counterpart (`corpus-port.ts:8-10`), and nothing in the package reads `ArtifactReference.path` at all -- so the public branch has neither a port to await nor an existing reader whose bytes could be reused. Recomputing its digest would mean adding a byte read of a caller-named path, a second effect this story does not otherwise need, for a branch no routed deferred-work entry names. It stays out of scope on that ground rather than on a claim that some existing code already reads it. Settled here rather than escalated, per standing instruction against further spine/ADR churn.

**Decision 4: `score` takes an optional `--private-manifest` CLI input.** No stage row declares `private-artifact-manifest` as an input anywhere in `STAGE_SIGNATURES` (Story 8.1 already routed this out on that ground), so there is no artifact-chain path that hands it to `score.ts` automatically. The command exposes it as its own optional flag — present, its entries are checked; absent, the check is skipped, matching AD-14's "one orchestration call" holding no policy about whether a manifest is required.

**Decision 5: the CLI gains a `--corpus-root` flag and builds the corpus port in `main.ts`.** The digest checks need `CorpusPort.resolve`, and nothing in `cli/` has ever held a port: `main.ts`'s `environmentOf` builds a `RunEnvironment` of file and stream effects only, `run.ts`'s `ApplicationFacade` (`:49-59`) holds three synchronous calls, and `runPreflight` -- the one existing port-awaiting application entry -- has no command for exactly this reason. Three constructions were available. Threading the port through `RunEnvironment` mixes an AD-8 port into a struct whose every other member is a stream or a filesystem primitive. Making the port optional on `RunScoreOptions` and skipping the checks when absent leaves the two digest matrix rows unreachable from the CLI, which fails VFR-8's parity rule in the same story that cites it. So the port is constructed in `main.ts` from `createLocalCorpusAdapter({ root })` behind a `--corpus-root` flag and passed as a member of `ApplicationFacade`'s `runScore` options, alongside an `AbortSignal` from a `main.ts`-owned `AbortController` -- the same shape `RunPreflightOptions` already declares. `--corpus-root` is optional; absent, `score` resolves no private reference, and a `--private-manifest` entry or a private-storage `isolationManifestArtifact` supplied without it is a usage error naming the missing flag rather than a silently skipped check.

**Round 2 addendum to Decision 5:** the shipped construction threads the port through `RunEnvironment` after all, the option this decision names and rejects. `RunEnvironment` gains `corpusPort: (root: string) => CorpusPort` and `signal: AbortSignal` (`run.ts:43-51`); `runScoreCommand` reads both off `environment` and only then assembles them into `RunScoreOptions` at the `application.runScore(...)` call site (`run.ts:~512`), so the "passed as a member of `ApplicationFacade`'s `runScore` options" half is true only at that last hop, not end to end from `main.ts`. Two things this decision's own rejection did not weigh: `run.ts`'s own header states "every effect is a member of `RunEnvironment`, so this module touches no stream, no `process`, and no Node builtin, and its tests run in memory" -- a port constructed outside that struct would be the one effect breaking that invariant and the one effect `tests/cli/run.test.ts`'s fake `environmentOf` could not fake the same way it fakes every other one; and `cli/` may import `application/` and `adapters/` only (`check:layers`'s own matrix), so `run.ts` cannot name `CorpusPort`'s type without going through `RunScoreOptions['port']`, making a bespoke non-`RunEnvironment` threading path awkward to type as well as inconsistent with the module's own stated convention. The mixing concern the original text raised is addressed by making the member a factory (`(root) => CorpusPort`) rather than a constructed port sitting inertly on the struct -- an effect invoked with an argument, the same shape every other `RunEnvironment` member already has, not a foreign value type.

**Decision 6: `CommandOutcome`'s `'verdict'` variant widens to `Verdict | null` rather than mapping the Invalid rung onto another outcome kind.** `LadderResolution.verdict` is `Verdict | null` (`ladder.ts:199`) and the Invalid rung resolves `null` with `exitCode: 3` (`ladder.ts:794-801`), while `CommandOutcome`'s variant declares `verdict: Verdict` (`exit-codes.ts:25`). Reusing the `'preflight'` kind's `passed: false` would reach the same 3 by a route that names the wrong stage in a CI reader's eyes, and inventing a fifth `Verdict` member breaks AD-11's published enum. Widening the field is the only option that keeps one outcome kind per producing surface: `verdictExit` returns `EXIT_INVALID` on `null` before its FAIL and CONCERNS clauses, so the `--strict` branch is unreachable for it and no promotion applies. Settled here rather than escalated, per the standing instruction against further spine or ADR churn.

**Round 2 addendum to Decision 6 and the Code Map's `exit-codes.ts` entry:** both the Code Map's `src/cli/exit-codes.ts:20-70` bullet and Round 1's third finding describe the `'verdict'` variant's boolean as `evidenceConditionsOnly`, sourced from `ladder.strictPromotable` as its negation. What shipped instead deletes that field: `CommandOutcome`'s `'verdict'` variant carries `exitCode: number` and `strictPromotable: boolean`, both read straight off `LadderResolution` with no inversion, and `verdictExit` checks `outcome.strictPromotable` directly. This is the reading the frozen Boundaries' own ban on "carrying an independently-computed `evidenceConditionsOnly`" (`exit-codes.ts:20-70` bullet) actually calls for -- negating `strictPromotable` into a same-shaped local field is still an independently-computed derivative of it, just one arithmetic step removed from a plain copy. The Code Map bullet and Round 1's finding both still name a field that does not exist in the shipped code; this addendum is the correction, not a rewrite of either.

**Decision 7 (implementation): score's InputKey set and flag names, and `--run-id` stays absent.** The Code Map's own list of score's inputs ("sealed-run-record, isolation-manifest, evaluator-configuration, contract, probes, preflight-verdict, policy, and an optional private-manifest") names artifact kinds in prose, not literal flag spellings: `INTERCHANGE_ARTIFACTS`'s own registry key is singular `probe` (`artifact.ts`), and `ScoreStage` takes exactly one `Probe`, never an array, so the new `InputKey` is `probe` with flag `--probe`, distinct from preflight's existing `--probes` array. The other seven keys are `record`, `isolation-manifest`, `evaluator-configuration`, `contract` (reused), `preflight-verdict`, `policy`, and `private-manifest`, each auto-deriving its own `--flag` from the existing `--${key}` convention. `score` takes no `--run-id`: `SealedRunRecord.runId` already supplies the run identifier through `ingest`/`score`, so `TAKES_RUN_ID.score` is `false`, unlike `preflight`. `isolation-manifest`, `evaluator-configuration`, and `private-manifest` are optional even though `INPUT_KEYS.score` declares all eight, which needed generalizing `parseCommand`'s missing-flags check (previously hardcoded to exempt only `'in'`) into a small `OPTIONAL_INPUT_KEYS` set; `'in'` joins the other three keys in it rather than gaining a parallel special case.

**Decision 8 (implementation): sourcing `emit`'s three caller-attested digests.** None of `evaluatorConfigurationDigest`, `fixtureDigest`, or `corpusDigest` has an artifact source the Code Map names explicitly. `evaluatorConfigurationDigest` is `record.evaluatorConfigurationDigest`, which `ingest`'s own agreement check already cross-verifies. `fixtureDigest` is `preflightVerdict.fixtureDigest`: `PreflightVerdict`'s own schema description states plainly that AD-10 makes this field required and "AD-11 names it as one of the scoring version's five inputs," the identical concept `emit` wants, so it is restated off an already-declared input rather than reinvented as a flag. `corpusDigest` has no such home: the architecture spine's own AD-27 rule text says "the corpus digest is recomputed from resolved bytes per AD-8," but this story's own scope, per its Intent and Code Map, is exactly two named digest-verification obligations (the private-manifest entries and the isolation-manifest-artifact reference) and never a general corpus-digest computation, and no file under `core/canonical/` is in the Code Map to build one against. It stays an explicit, required, caller-attested `--corpus-digest <digest>` flag, validated against the `Digest` primitive before use, the same posture `--run-id` already takes for a value with no JSON artifact behind it. Settled here rather than escalated.

**Round 2 addendum to Decision 8:** "the same posture `--run-id` already takes" overstates it. `--run-id`'s own guard (`arguments.ts`, `.trim() === ''`) runs at the argument surface and fails as a usage error, exit 64; `--corpus-digest`'s `Digest`-format check runs inside `application/score.ts` and fails as a `schema-parse-failure` `RuntimeFault`, exit 5 -- a fault, not a usage error. The shared ground the sentence was reaching for is narrower than it said: neither value has a JSON artifact behind it, so neither is read via `readJson`, and both are still checked somewhere before use rather than passed through unchecked. The exit code differs because the checks differ in kind: `--run-id`'s is a CLI-level usability guard over a value the schema (`z.string().min(1)`) already accepts as legal but useless (a whitespace-only run id), while `--corpus-digest`'s is the same content-shape validation every other artifact-shaped input on this CLI receives at the application layer (`--record`, `--contract`, and the rest all fail as `schema-parse-failure` faults on a malformed value, never as a usage error) -- so leaving it as a fault is the consistent choice, not a gap to close by moving it to the argument surface.

**Decision 9 (implementation): `waiver` and `evaluationFault`, `score()`'s two caller-supplied parameters with no declared-input source, are fixed at `'none'` and `false` inside `application/score.ts`.** Neither the contract nor the sealed run record carries a value for either; `scripts/worked-example-target.ts`'s own hand-assembly hit the identical gap and recorded its reasoning inline: "the contract declares no waiver ... and the run recorded no AD-26 evaluation fault. All three arrive declared." `application/score.ts` mirrors that precedent rather than inventing a new default.

**Decision 10 (implementation): `runScore`'s return type widens to `{ artifact: EvidenceArtifact | null; ladder: LadderResolution }`, and `emit` is never called on the Invalid rung.** `emit.ts`'s own module comment states that a run reaching the Invalid rung "is the caller's own signal to stop before minting an artifact at all," mirroring `worked-example-target.ts`'s own `if (ladder.verdict === null) fail(...)` guard immediately before its `emit` call; `emit.ts` casts `scored.ladder.verdict as Verdict` unconditionally and is not in this story's Code Map to change, so calling it on a `null` verdict would either mint a schema-invalid artifact or throw a bare `TypeError` with no exit-3 mapping, contradicting the I/O Matrix's own "exit 3" row. `runScoreCommand` skips `emitArtifact` when `artifact` is `null`, so nothing is written for `--out` on that rung. The frozen I/O Matrix's "artifact written" wording for the Invalid-rung row describes the ordinary case; the Invalid rung is the one row with no legal `EvidenceArtifact` to write, since the schema has no `Verdict` member standing in for `null`. Settled here rather than escalated, per the standing instruction against further spine or ADR churn; flagged for the human's awareness since it reads against the frozen Intent block's literal text.

**Decision 11 (implementation): the `--corpus-root`-missing usage error lives in `cli/run.ts`, not `application/score.ts`.** A usage error (exit 64, rendered via `renderUsage`) is `cli/`'s own vocabulary; `application/` only ever returns a result or throws `StructuralFailure`/`RuntimeFault`. `runScoreCommand` reads every input, then checks (over the same unvalidated JSON, defensively) whether a `--private-manifest` entry or a private-storage `isolationManifestArtifact` is present with no `--corpus-root` given, and returns `{ outcome: { kind: 'usage-error' } }` before ever calling `application.runScore`. `RunScoreOptions.port` stays optional for a programmatic caller; `runScore` itself throws a plain `TypeError` (never a `RuntimeFault`, matching `emit.ts`'s own "reachable only through a type-system bypass" precedent) if it is ever reached needing resolution with no port. The CLI's own pre-check makes that unreachable through the shipped binary for a non-empty `--private-manifest` or a private-storage `isolationManifestArtifact`; a zero-entry `--private-manifest` needed a second guard inside `application/score.ts` itself, added in Round 2 after peer review found it reachable (see Round 2's blocking finding, above).

## Design Notes

`runScoreCommand` mirrors `runPreflightCommand` (`run.ts:296-328`): read each declared input via `readJson`, assemble the options object, call the one application-layer function, `emitArtifact`, return. The two digest checks are additive steps inside `application/score.ts` between reading inputs and calling `ingest` — corpus-port resolution and comparison, then `ingest`/`score`/`emit` proceed unchanged regardless of outcome (a mismatch is a `RuntimeFault`, exit 5, same class as any other thrown fault this layer already propagates, per `preflight.ts`'s own fault-propagation precedent).

epics.md's AC names `docs/explanation/roadmap.md` for the "Nothing in the current release computes contract strength" sentence; that literal sentence lives in `docs/index.md:78` instead, with a same-shape sibling in `docs/explanation/behavioral-evaluation-contracts.md:163`. All three files' stale sentences are corrected in this diff regardless of which file epics.md named, since the point of the AC — no doc claims scoring is unreachable once it ships — survives the misattribution.
