## Intent

**Problem:** Every declaration `Operation` carries is an HTTP declaration. `method` (`src/core/schemas/interface.ts:120`) is the closed seven verbs at `:93-101`, `pathTemplate` (`:121`) is a slash-rooted template at `:109`, `requestShape` (`:127`) is the four transport channels at `:83-90`, and `responseDescriptor` (`:128`) is six fields `src/core/compile/bindings.ts:38-48` says are every one of them about a JSON body. A command-line system under test has none of these. Its operations are subcommands, its inputs are positional arguments, options, environment variables, and standard input, and its outputs are two text streams, an integer, and the files it wrote. So the first contract authored outside this repository can parse only by declaring a meaningless `POST /path`, and then fails compilation anyway under `unsupported-interface-kind` (`src/core/compile/interface-inventory.ts:12-22`).

**Approach:** Make `permittedInterfaces` a union discriminated on `kind`. The `api` member carries today's `PermittedInterface` byte for byte, and `web` and `mcp` carry the same shape, so every existing contract and fixture parses unchanged and `unsupported-interface-kind` keeps three firing conditions. A fourth `cli` member carries a command operation: the same `operationId` and `stateChangeMarker`, a logical `invocation` in place of the method and path template, a request shape over four command channels, a bare list of the artifacts it writes, a declared descriptor root, and exactly one `responseDescriptor` describing whichever channel that root names. The plan-side and pre-flight-side shapes that mirror the request shape move with it. Nothing in `compile` changes here; a command contract parses at the end of this story and still fails compilation, which is the state the next two stories close.

## Boundaries & Constraints

**Always:**

- All four kinds parse. `interface.ts:152-154` states the rule this story must not break: "All four kinds are admitted so `unsupported-interface-kind` stays fireable. v0 supports `api`; the other three fail compilation under that code rather than failing to parse." A union that made `web` or `mcp` a parse failure would delete two of that code's three firing conditions.
- The `api` member is unchanged in shape and in published bytes wherever the export can keep them. Every existing fixture, every corpus contract, and `gateCContract` parse without edit.
- AD-35 binds the invocation. Its rule is that "a contract names logical interface identifiers only and never a URL, host, or port. The caller maps those identifiers to authorized targets through configuration outside the contract, so a contract cannot choose what is contacted." An absolute or relative filesystem path to an executable is the same disclosure, so the invocation names a logical executable and the caller maps it.
- AD-19 requires a transport identity per operation, because "AD-40 resolved a defect signature by asserting that 'method and path template are declared per operation under AD-19'". The command operation declares one that plays the same role and admits the same erasure, or AD-40's resolution has nothing to bind against in Story 9.4.
- The eval contract takes one BREAKING `schemaVersion` bump, 3 → 4, recorded in the driving field's own `.describe()` per AD-11. `tests/schemas/eval-contract-version.test.ts:51`'s `EVAL_CONTRACT_SCHEMA_VERSION` is raised first, and its failures name every literal that has not moved.

Only an `ADR-nnn Decision n` prefix is exempt from the last. `check:boundary` fails the build on each of the twelve, and the adjacent repository whose contract motivates this epic carries one of them in its name, so it is never written into `src/` or `corpus/`.

## Decisions settled by construction

**Decision 1: the union has four members and `web` and `mcp` keep the `api` operation shape.**
A two-member union (`api` and `cli`) makes a `web` or `mcp` contract a parse failure. `interface.ts:152-154` states the shipped rule that all four kinds parse "so `unsupported-interface-kind` stays fireable", and AD-10's own sentence is that v0 "fails compilation honestly under `unsupported-interface-kind` for `web`, `cli`, and `mcp` rather than leaving three kinds to implementer invention." A parse failure is not an honest coded failure: it carries no AD-5 code, no artifact path, and no name for the thing that is unsupported. So `web` and `mcp` carry `Operation` unchanged, and after Story 9.3 the code has two firing conditions where it has three today. Downstream consequence: Story 9.5's disclosure says the code narrowed rather than that it was removed, and Story 9.3 inherits the obligation to keep a fixture per surviving condition. Known-bad state avoided: a contract naming `mcp` getting an anonymous schema rejection where a reader used to get a code naming the unsupported kind.

**Decision 2: the command's transport identity is a logical executable plus a subcommand path, and it is an `Identifier` rather than a free string.**
AD-19 names method and path template because "AD-40 resolved a defect signature by asserting that 'method and path template are declared per operation under AD-19', which was the load-bearing repair by which it withdrew an unsatisfiable citation, and it rested on a declaration that did not exist." A command identity has to carry the same weight: contract-independent, comparable, and authorable by a probe seeder who has never seen the contract. `Identifier` is what makes AD-35 structural instead of advisory. A free string admits `/usr/local/bin/tool`, `./tool`, `C:\tool.exe`, and `http://host/tool`, and every one of those is the disclosure AD-35 exists to prevent, stated in a different alphabet; `Identifier`'s charset admits none of them, so the rule is enforced by parse rather than by a compile check nobody wrote. The subcommand path is a list rather than one string for the same reason `PathTemplate` spells parameters in braces and nothing else (`interface.ts:103-108`): AD-40 compares identities as segments, and a single string forces two implementations to agree on a separator that no field declares. Downstream consequence: Story 9.4's `operationSignature` counterpart joins the executable and the subcommand path with a separator declared in one place, and Story 9.3's `duplicate-operation-signature` check compares the joined form.

**Decision 3: parameter erasure has no command counterpart, and the identity is compared literally.**
`operationSignature` (`interface-inventory.ts:36-41`) erases `{name}` before comparing, because "a signature is authored against a corpus and parameter naming is exactly the contract-local choice this paragraph moved off" (AD-40). A subcommand path carries no parameters: a command's variable inputs are its arguments and options, which live in the request shape rather than in the identity. So the command identity is compared literally, and the erasure function stays HTTP-only. This is recorded rather than assumed because the symmetry is tempting and wrong: erasing a subcommand segment would make `tool review` and `tool report` one signature. Downstream consequence: Story 9.4's signature resolution branches on kind before comparing, and Story 9.3's duplicate check does the same.

**Decision 4: a command operation carries exactly one `responseDescriptor`, a tagged `descriptorChannel` naming the channel it describes, and a bare list of artifact identifiers. The four-named-parts descriptor is the option turned down.**
An earlier draft of this story gave the command operation a `CommandOutputDescriptor` with four named parts: a structure declaration for standard output, one for standard error, a declared success value space for the exit code, and an array of artifact records each carrying its own `ResponseDescriptor`-shaped body declaration. An adversarial review killed it on AD-19 and AD-20, and the reasons are the ADs' own words rather than a preference.

AD-19 fixes the descriptor per operation, and the sentence it fixes it with is about having one referent: "The per-operation descriptor gives `requiredKeys` a truthful value, gives rule 2 an exact denominator, and makes pointer reachability, collection typing, channel roles, success indicators, and volatile-pointer exclusion resolve through the operation named by the interaction-plan step." AD-20 rule 2's satisfaction reads "the required keys of the response descriptor belonging to the operation that step invokes". An operation carrying one descriptor per artifact leaves that phrase with several candidate referents and leaves rule 2 with no truthful denominator, which is precisely the defect AD-19 records one level up for an interface-wide union ("one interface-wide union descriptor is vacuous in the ordinary multi-shape case: operations returning a job resource, a page of rows, and an error share no required key"). The rejected shape moved that defect inside the operation instead of across it, which is worse rather than better, because across it there was at least a per-operation escape.

`exitCode.successValues` failed on a second ground. AD-19 already declares a nominated success indicator per operation and states what it is for; a declared success value space beside it is a second success-indicator concept, and two concepts answering one question is the shape AD-19's own "the success indicator and the sibling groups exist because AD-31's predicates for rule 1 and rule 5 are otherwise undecidable" was written to avoid. An exit-code assertion needs no declaration at all: it is an oracle over `/interactions/<step>/exit-code`, which the pointer grammar already carries as a scalar channel (`pointer.ts:57-60`).

So the shape is one `responseDescriptor`, a `descriptorChannel` saying which channel it describes, and `artifacts` as bare identifiers with existence semantics only. Every AD-31 predicate keeps reading exactly one descriptor object, one dereference deep, which is what `relevance.ts:62,108,171,240` already do. Downstream consequence: Story 9.2's `artifact` pointer resolves its identifier segment against the `artifacts` list and fires `unresolved-artifact-reference` on a miss, and Story 9.3's per-kind branches read `responseDescriptor` on both kinds, with only the pointer prefix differing by root. A command whose standard output and whose written report both need declared structure is a genuine expressive limit of this shape, and it is recorded here rather than solved: the contract declares the descriptor for the channel its oracles actually read, and an operation needing two is two operations.

**Decision 5: `InputBinding` and `WitnessInputs` become structural unions with no discriminator, and the agreement with the operation's kind is a compile-time check rather than a schema refinement.**
An interaction step names an `operationId` and nothing else; the kind of the interface declaring that operation lives in a different subtree of the same document. Zod can express that as a root refinement and the published export cannot carry it, which is the defect `plan.ts:34-37` already records for `{ principal }`: "a Zod refinement here would be a cross-subtree constraint the export cannot carry, and the published-schema differential sweep synthesises a union-branch witness that would expose the disagreement." Adding a `kind` field to the step itself was the other option and is turned down: it duplicates a fact the operation already carries, and a step whose declared kind disagrees with its operation's is a second inconsistency to check rather than one fewer. So both shapes are plain unions, a step binding HTTP channels against a command operation parses, and the disagreement is one of the two conditions Story 9.2's new code fires on. Downstream consequence: Story 9.2 owns the code and Story 9.3 owns the thrower, and until Story 9.3 lands, a mismatched binding is admitted by every gate. That window is real and is why the two stories are adjacent.

**Decision 6: `Operation` gains a `.meta({ id })` and the published eval-contract schema changes shape as a result.**
Three of the four union branches carry the identical operation shape. Without an id, Zod inlines it three times and `schemas/eval-contract.schema.json` grows by two full copies of a large object, which moves every census literal and every keyword-occurrence count for no semantic gain. `plan.ts:45-48` is the shipped precedent for the opposite choice and states its own cost exactly: "an id would collapse the branches to `$ref`s and mint new `$defs`, so the export stays byte-identical." There the goal was byte-identity; here the export is already breaking, so the byte-identity argument does not apply and the `$defs` entry is the cheaper shape. The consequence is stated rather than discovered: a non-TypeScript consumer that previously read the operation shape inline now follows one `$ref`, which is a published-surface change and is disclosed in Story 9.5 alongside the version bump. Known-bad state avoided: three divergent copies of one shape in the published document, which is the drift the Consistency Conventions' Naming row warns about arriving through the export instead of through the source.

**Decision 7: `sensitivityWitness` stays required-and-nullable on the command operation, on the api operation's own terms.**
`interface.ts:130-132` says `null` "is legal only for an operation declaring no keys in any request channel; AD-10 exempts that operation and requires the exemption to be recorded, which pre-flight does as an `exempt` check. An input-bearing operation declaring `null` fails a strict compilation under `undeclared-mandatory-input`." A command operation that takes no arguments, no options, no environment, and no standard input is exactly AD-10's exempt case, and one that takes any of them is not. Nothing about that rule is transport-specific, so it carries over unchanged and `checkSensitivityWitnessDeclared` keeps one rule for both kinds once Story 9.3 teaches `declaresNoRequestKeys` (`src/core/declared-inputs.ts:16-25`) to read the command channels. Downstream consequence: Story 9.3 inherits `declaresNoRequestKeys`, `suppliedKeys` (`src/core/compile/sensitivity-witness.ts:38`), and `checkInputsAgainstShape` (`:76`), all three of which loop `TRANSPORT_CHANNELS` today.

**Decision 8 (WITHDRAWN, replaced by Decision 11): reachability has no opinion about a non-api step, and says so by returning reachable rather than by resolving nothing.**
`checkEvidenceReachability` runs at `compile.ts:83` and `checkInterfaceKind` at `:98`, so every contract carrying an unsupported kind passes through fifteen checks before the one that names its actual defect. `evaluateReachabilityAgainstOperation` (`reachability.ts:250-351`) reads `responseDescriptor` at `:277` and `requestShape` at `:330`, and a command operation has neither, so it cannot be resolved through `operationOf` without either widening that return type here (Story 9.3's work, twenty call sites) or letting the lookup miss. Letting it miss produces `unreachable-check-evidence` with the reason "names operation X, not declared by any permitted interface", which is a false statement about a contract that declares the operation perfectly well, reported under a code that outranks the true one. So `evaluatePointerReachability` checks the declaring kind first and returns `reachable()` for any kind but `api`. That is not a claim that the pointer is fine; it is the absence of a claim from a function whose every rule is a statement about an api operation's declared shape, and the contract still fails fifteen calls later under the code that names the real condition. Both replacements are already committed: Story 9.2 replaces the blanket deferral for `cli` with the real per-kind channel rule, and Story 9.3 replaces it with the descriptor-shaped rules once `operationOf` returns the union. Known-bad state avoided: a contract that declares its operations correctly being told they are undeclared.

**Decision 9: `stdin` is a keyed declaration on the request shape and a tagged body value on a witness leg, which is exactly the asymmetry `body` already has.**
Three sites in Story 9.3 would each guess at this, so it is settled here. `RequestShape.body` (`interface.ts:89`) is a `KeyedShapeDescriptor`, because a declaration says which keys an operation accepts and what type each carries. `WitnessInputs.body` (`sensitivity-witness.ts:22`) is a `ProbeRequestBody`, because one probe leg supplies a value and has to tell an absent body from one carrying JSON `null`, which a key map cannot express. `suppliedKeys` (`compile/sensitivity-witness.ts:38-49`) is the code that bridges the two, and its `if (channel !== 'body')` at `:42` is that bridge. `stdin` is the command analogue on both halves: `CommandRequestShape.stdin` is a `KeyedShapeDescriptor` and `CommandWitnessInputs.stdin` is a tagged body-like value, so `suppliedKeys` special-cases `stdin` alongside `body` and everything downstream keeps one rule. Decision 14 records why that tagged value is not `ProbeRequestBody` itself. The census this story owns is that five shapes carry the four transport channels, and the `stdin`-and-`body` exception is recorded against each: `RequestShape`/`CommandRequestShape` keyed on both, `InputBinding`/`CommandInputBinding` a `BindingChannel` key map on both, `ObservedCallInputs` (Story 9.4) a nullable object on both, `ProbeInputBinding` (Story 9.4) a `ProbeBindingChannel` key map on both, and `ApiWitnessInputs`/`CommandWitnessInputs` the one shape where the value spelling diverges. Downstream consequence: Story 9.3's `bindsTypeViolating` (`satisfaction.ts:353-359`) and `checkSelectorKeys` still range over `stdin` as a key channel, because a binding is a key map on every one of the five; only `suppliedKeys` and `checkInputsAgainstShape` meet the value spelling.

**Decision 10: only the sensitivity leg's inputs take the union, so the probe artifact does not move.**
`WitnessInputs` is embedded four times: on `SensitivityWitnessLeg`, which is the eval contract's; on `FixtureReset`, also the eval contract's; and on `ManifestationWitness`, which rides on `Defect` and therefore lands on the **probe**. Widening the shared name would retype the probe in the same change that retypes the eval contract, which is a second artifact's `schemaVersion` bump landing in a step that owns one. The choice made is neither of the two the review offered: the union is introduced under its own name and only `SensitivityWitnessLeg.inputs` references it, while `ManifestationWitness.inputs` and `FixtureReset.inputs` stay `ApiWitnessInputs`, which is the shipped shape under a new name and therefore byte-identical in the export. The probe's regenerated document differs by nothing but the interaction pointer's widened pattern.

This is truthful rather than merely convenient, and the reason is the same one that keeps pre-flight closed to a command interface: both of those legs are issued through the environment-probe port, whose `ProbeRequest` carries a method, a path template, and the four transport channels. A command leg has none of them, so a command manifestation witness would declare work no port can run. Downstream consequence: the step that teaches pre-flight to run a command also widens those two fields and takes the probe's bump with it, and a command contract cannot declare a fixture reset until then. Known-bad state avoided: a probe artifact whose schema admits a leg the shipped port cannot issue.

**Decision 11: reachability descends through the operation's own declared output channel, and that replaces Decision 8's blanket deferral.**
Decision 8 proposed returning `reachable()` for every non-api step, on the ground that resolving a command operation through `operationOf` would either widen that return type here or let the lookup miss. Both halves of that reasoning survive; the conclusion does not. Counting the evidence pointers across the nine contracts authored outside this repository: 110 address `stdout` with a one-segment tail, 18 address a written artifact, and 1 addresses the exit code. A blanket deferral would let all 110 pass by abstention, and the rule that decides them would arrive a step later against contracts that had already been declared reachable.

`reachability.ts:257-266` returned `unreachable` for any tailed `stdout` pointer, on the stated ground that "stdout/stderr are always bare strings". That statement is true of an api operation and false of a command operation that nominates standard output as the channel its descriptor describes. So the repair is not a per-kind branch but a generalisation: AD-19 gives every operation exactly one response descriptor, `descriptorChannelOf` says which channel it describes, and the descent that used to be spelled for `response-body` is now spelled once and reached from whichever channel the operation nominates. `response-body` off an interface that speaks HTTP and `stdout` off a command are two roots of one rule, and the artifact channel becomes a third case of a rule already written rather than a fourth rule.

The same generalisation lands in three more places that hard-coded the body: `checkCapturedChannel`'s capturable channel, `capturedType`'s reasons, and `checkQuantifierOverNonCollection`'s channel test, which now resolves the operation before testing the channel because which channel carries declared structure is the operation's own answer. `evaluatePointerReachability` resolves through `anyOperationOf`, so a command operation is resolved rather than missed, and `operationOf` stays narrow. Downstream consequence: the step that adds the artifact channel adds one member to `CommandDescriptorChannel` and one case to `descriptorChannelOf`, and every consumer follows. Known-bad state avoided: 110 pointers admitted by a function that has no rule for them.

**Decision 12: a command witness admits all four command channels, because AD-10's marker rule decides nothing off HTTP.**
AD-10 selects `path` or `query` where the state-change marker is false and `body` where it is true, and the reason is transport-specific: an HTTP read carries its identifier in the URL and a write carries it in the body. A command carries its inputs the same way whether or not it changes state, so the marker selects nothing. `COMMAND_WITNESS_CHANNELS` is therefore all four and the author picks the channel their operation is actually sensitive on. Downstream consequence: `checkWitnessLegality`'s marker check is a no-op on a command operation, and any later rule that wants to narrow it has to name a command-side reason the marker does not supply.

**Decision 13: the command witness leg is spelled inline rather than named, and the reason is the mutation sweep rather than size.**
Giving `CommandWitnessInputs` a `.meta({ id })` puts it in `$defs` beside `WitnessInputs`, and both are then reached through one `anyOf`. A `$ref`'d definition's own errors reach ajv with a schema path relative to that definition, so both report a bare `#/required` and `#/additionalProperties` at the same instance path and nothing tells them apart. AD-13's mutation sweep requires one keyword deletion to be attributable to one occurrence, and its attributability test refuses a mutant whose rejection also trips a sibling keyword at the same instance path; with two `$ref`'d branches over disjoint key sets, every single mutation trips both. Spelled in place, the command branch's occurrences carry their full path and both branches become attributable again. The cost is two copies of a four-key object in the published document, which is small and is stated on the shape itself. Known-bad state avoided: four published keywords that no fixture can be shown to kill.

**Decision 14: a witness leg writes standard input as `json`, `text`, or `absent`, and a text stream is exempt from that channel's key comparison.**
`ProbeRequestBody` has two arms, `json` and `absent`. Every one of the driving contracts spells a supplied standard input as `{"kind": "text", "value": "..."}`, and it is right to: standard input is a byte stream, so a command that reads a prompt receives text that was never JSON, and routing it through the `json` arm as a JSON string would make the leg claim a serialisation the command never sees. `ProbeObservedBody` already carries a `text` arm for the same reason on the other side of the boundary, so `ProbeRequestStdin` is declared with all three and `ProbeRequestBody` is untouched.

That leaves a second question the review's "no action needed" did not reach. `CommandRequestShape.stdin` is a `KeyedShapeDescriptor`, so an operation declares `stdin` keys, and a leg supplying raw text says nothing about which of them the text fills. `checkInputsAgainstShape` therefore abstains on a channel supplied as an opaque stream rather than asserting against an enumeration that does not exist. The question that check actually asks is whether the port can issue the request, and for a text stream it can. Downstream consequence: an operation whose standard input is genuinely a JSON object still gets the full key comparison, because such a leg supplies the `json` arm; only the opaque spelling abstains.

**Decision 15: AD-10 has a third situation and no exemption for it yet, and the failure message says so.**
`checkSensitivityWitnessDeclared` demands a witness from any operation declaring request keys, and exempts only an operation declaring none. One of the nine driving contracts is neither: its workflow is stack-neutral by design, so its two cases mandate the identical output and a differential relation demanding they differ would be a demand no source supports. Narrowing "declares request keys" to channels that could differentiate is the cheaper repair and is wrong here, because `stdin` can differentiate in general and it is this system that is insensitive; the narrowing would delete the check for the whole kind. A declared exemption carrying the author's reason is the honest shape and is not built here, because it is a required-and-nullable field on both operation shapes and therefore moves every contract literal in the tree for a capability no contract in this tree uses.

What this step ships instead is the part that costs nothing and is owed either way: the failure message now names the third situation and says why the obvious workaround is not one. Declaring a witness whose relation asserts the two legs agree satisfies the check and proves nothing, since a hard-coded response satisfies it too, so an author told only "declare a witness" is being told to write a false oracle. Downstream consequence: the step that adds the exemption field adds it to both operation shapes under the eval contract's next bump, and this message is what it replaces.

## Design Notes

The organising idea is that the discriminator already exists and nothing reads it. `kind` has been on `PermittedInterface` since the first schema and its only consumer is a check that throws. Making the operation shape depend on it costs one union and buys a second interface kind; the alternative, a fifth optional field bag on one flat operation, buys a shape where every command contract declares four HTTP fields it does not mean and every api contract declares four command fields it does not mean, and no predicate can tell which half is load-bearing.

The shape, for orientation only:

```ts
export const CommandInvocation = z.strictObject({
	executable: Identifier, // AD-35: a logical name the caller maps, never a path
	subcommand: z.array(Identifier), // compared segment by segment, never erased
})

export const CommandOperation = z.strictObject({
	operationId: Identifier,
	invocation: CommandInvocation,
	stateChangeMarker: z.boolean(), // AD-20 rule 7 and AD-10 both read it
	requestShape: CommandRequestShape, // argument, option, environment, stdin
	artifacts: z.array(Identifier), // existence only, no descriptor, no keys
	descriptorRoot: CommandDescriptorRoot, // tagged: which channel the descriptor describes
	responseDescriptor: ResponseDescriptor, // exactly one, AD-19's own shape
	volatilePointers: z.array(DescriptorPointer),
	sensitivityWitness: SensitivityWitness.nullable(),
})

export const PermittedInterface = z.discriminatedUnion('kind', [
	/* api */ commonInterface('api', z.array(Operation)),
	/* web */ commonInterface('web', z.array(Operation)),
	/* mcp */ commonInterface('mcp', z.array(Operation)),
	/* cli */ commonInterface('cli', z.array(CommandOperation)),
])
```
