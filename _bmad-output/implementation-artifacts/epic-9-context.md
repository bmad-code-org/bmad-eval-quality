# Epic 9 Context: the interface kind a contract can describe

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

Epic 9 opens the contract language to a second interface kind.
`TEST-PLAN-NEXT-STEPS.md:315-328` makes the first eval contract authored outside this repository the entry criterion for v1, and says of a failure that "a change needed here is the finding, and it names which part of the schema or which failure code did not carry enough information to author against."
The first such contract is a behavioural contract for a command-line system under test in the adjacent `bmad-method-test-architecture-enterprise` repository, and it cannot be authored: every declaration the contract carries about an operation is an HTTP declaration, and `checkInterfaceKind` (`src/core/compile/interface-inventory.ts:12-22`) rejects `kind: "cli"` outright.
The epic's tractability rests on an asymmetry the source already carries: the evidence side of the addressing grammar is command-aware and the declaration side is not.
`EVIDENCE_CHANNELS` (`src/core/schemas/pointer.ts:12-20`) already carries `stdout`, `stderr`, and `exit-code`, and `Observation` (`src/core/schemas/sealed-run-record.ts:171-211`) already records all three at `:203`, `:204`, and `:205-210`.
What is missing is a way to *declare* a command, a channel for a file the system under test wrote, and a compiler that will admit either.
When the epic ends, a command-kind contract compiles, seals, pre-flights, scores, and ships in the dev corpus, and the epic's breaks are disclosed the way Story 7.10 established.

## Stories

## The eight measured findings this epic exists to close

Each is restated from the failed authoring attempt against the published 0.2.0 surface, and each is verified against the source in this tree.

1. **`kind: "cli"` parses and then fails compilation.** `PermittedInterface.kind` (`src/core/schemas/interface.ts:152-154`) admits all four kinds so the code stays fireable, and `checkInterfaceKind` (`interface-inventory.ts:12-22`) throws `unsupported-interface-kind` on every kind but `api` at `:14`, with the message `"cli" is not supported in v0; only "api" is (AD-10)` at `:18`. `planPreflight` asserts the same thing a second time at `src/core/preflight/plan.ts:239-250`.
2. **`Operation` requires an HTTP verb and a path template.** `Operation` (`interface.ts:118-133`) declares `method: HttpMethod` at `:120` over the closed seven at `:93-101`, and `pathTemplate: PathTemplate` at `:121` over `PATH_TEMPLATE_PATTERN` (`:109`). A command invocation has neither, so a command contract parses only by declaring a meaningless `POST /path`.
3. **`requestShape` is the four HTTP transport channels.** `RequestShape` (`interface.ts:83-90`) is a four-key strict object over `path`, `query`, `header`, and `body`. A command's inputs are positional arguments, options, environment variables, and standard input.
4. **`sensitivityWitness.channel` admits three of those four.** `WITNESS_CHANNELS` (`src/core/schemas/sensitivity-witness.ts:47`) is `['path', 'query', 'body']`, and `WitnessInputs` (`:17-28`) is keyed by the same four HTTP channels.
5. **`responseDescriptor` describes one JSON body.** `ResponseDescriptor` (`interface.ts:45-70`) carries `requiredKeys`, `permittedKeys`, `types`, `successIndicator`, `channelRoles`, and `collectionLocations`, and `bindings.ts:38-48` states plainly that every one of the six "is about the body". A command's observable output is standard output, standard error, an exit code, and the files it wrote.
6. **The evidence side is already command-aware; only the declaration side is HTTP-only.** `EVIDENCE_CHANNELS` (`pointer.ts:12-20`) carries seven members including `stdout`, `stderr`, and `exit-code`; `TAIL_BEARING_CHANNELS` (`:50-55`) admits `stdout` and `stderr`, `SCALAR_CHANNELS` (`:57-60`) admits `exit-code`; `Observation` records all three; `projectChannel` (`src/core/score/quotation.ts:59-87`) projects all three; and `channelRoot` (`src/core/evaluate/evidence-resolution.ts:78-107`) resolves all three. This is what makes the epic a declaration-side change rather than a second product.
7. **There is no evidence channel for a file the system under test wrote.** The closed seven have no member for it, and `Observation` has no field for it. That is the dominant output shape for a command-line tool, and the subject system's own report and verdict are both files.
8. **AD-40's signature resolves on transport identity that a command does not have.** `DefectSignature` (`src/core/schemas/defect-signature.ts:133-143`) declares `method` and `pathTemplate` at `:137-138`, `operationSignature` (`interface-inventory.ts:36-41`) builds `"<method> <erased path>"`, and `qualifyProbe` rejects every kind but `api` at `src/core/score/qualification.ts:718-726` with the detail `"<kind>" declares a method and a path template that mean nothing off an api interface`.

## Requirements & Constraints

- **AD-10 is the AD that closed the kind and AD-10 is the AD that names the condition for opening it.** Its rule reads "Probe semantics are declared per interface kind; v0 supports `api` and fails compilation honestly under `unsupported-interface-kind` for `web`, `cli`, and `mcp` rather than leaving three kinds to implementer invention." The failure is honest because the semantics are undeclared. This epic declares them for one kind and leaves the other two failing, so the code stays fireable and the sentence stays true of `web` and `mcp`.
- **AD-19 is what a new kind has to satisfy.** Its rule requires per operation "its **method**, **path template**, **state-change marker**, request shape, closed response descriptor, **channel role** for each pointer that descriptor names, nominated success indicator, and volatile pointers per AD-11", and its own reason for naming method and path template is that "AD-40 resolved a defect signature by asserting that 'method and path template are declared per operation under AD-19'". The command kind must supply a transport identity that plays the same role, or AD-40's resolution has nothing to bind against.
- **AD-35 forbids more than a URL.** Its rule is that "a contract names logical interface identifiers only and never a URL, host, or port. The caller maps those identifiers to authorized targets through configuration outside the contract, so a contract cannot choose what is contacted." An absolute filesystem path to an executable is the same disclosure in a different alphabet, so a command invocation names a logical executable and the caller maps it, exactly as `logicalId` (`interface.ts:149-151`) already works.
- **AD-26's channel vocabulary is closed and its grammar is fixed.** Its rule spells the root as `/interactions/{stepId}/` followed by "one of the closed channel vocabulary `response-body`, `response-headers`, `response-status`, `call-inputs`, `stdout`, `stderr`, `exit-code`", and it fixes the transport-rooted form: "Under `call-inputs` the next segment is one of the four transport channels AD-19 declares ... revision 3 rooted `call-inputs` directly on a key name, which had no declared structure to resolve against." A new channel that names one of several written files has the same defect revision 3 had, so it takes the same repair: an identifier segment before its tail.
- **AD-11 governs every schema move.** "Adding an optional field is a `schemaVersion` bump recorded in the field's own description; removing or retyping is breaking." Every artifact this epic changes is retyped, so every bump is breaking, and each is recorded in the driving field's own `.describe()`. `CHANGELOG.md:56-125` is the shape the disclosure takes.
- **AD-5 is the registry and it is closed by amendment.** `FAILURE_CODES` (`src/core/failure-codes.ts:11-35`) carries twenty-three codes in the table's order, `check:ad5-registry` (`scripts/check-ad5-registry.ts`) enforces set-and-order equality against AD-5's own table, and `lint:spine` runs `--registry-ad 5` over the spine. A code minted here is appended to that table in the same diff, which is what Epic 7 did for `binding-cycle` and `captured-channel-undeclared` (`epic-7-context.md:32`). Editing that one table is a mechanical consequence of minting a code, not a spine revision.
- **AD-24 and AD-29 are untouched.** No stage row moves, no artifact changes owner, and no stage gains or loses a lineage edge. `STAGE_SIGNATURES` is read but not written.
- **AD-27 and AD-36 are untouched.** Every new field is a string, an integer, or a container of them, so the value domain and the canonical digest are unchanged.
- `check:boundary` scans `src/` (through `dist`), `corpus/`, and three `package.json` fields for twelve forbidden strings: `_bmad-output`, `planning-artifact`, `implementation-artifact`, `sprint-status`, `ARCHITECTURE-SPINE.md`, `bmad`, `TEA`, `stor(y|ies)`, `epics?`, `ACs?[- ]\d`, `Tasks?[- ]\d`, and `Decisions?[- ]\d`. The last one's lookbehind exempts any `ADR-nnn ` prefix. No source comment or corpus byte this epic writes may carry any of the twelve, and the adjacent repository's own name carries one of them, so it is never named in `src/` or `corpus/`.
- `test:coverage` includes `src/core/**` only, at 90% statements and 90% branches.
- Ambiguities found mid-story are settled by construction in that story's decisions section rather than escalated into a spine revision or a new ADR, as Epics 7 and 8 both established (`epic-8-context.md:29`). Each such decision names the later story that inherits it.

## Technical Decisions

- **The union is discriminated on `kind` and carries four members, not two.** AD-5's `unsupported-interface-kind` must stay fireable, and `interface.ts:152-154` already says so: "All four kinds are admitted so `unsupported-interface-kind` stays fireable. v0 supports `api`; the other three fail compilation under that code rather than failing to parse." A two-member union would make `web` and `mcp` parse failures rather than coded compile failures, deleting a shipped code's only firing condition. `web` and `mcp` therefore keep the `api` member's operation shape unchanged.
- **The declaration side and the addressing side split across Stories 9.1 and 9.2, and the command channel names are declared in 9.1.** `pointer.ts` owns the channel vocabulary today (`TRANSPORT_CHANNELS` at `:35`), so the command channel tuple is declared beside it in Story 9.1, where the request shape that reads it lives. Story 9.2 then wires those names into `INTERACTION_POINTER_PATTERN` (`pointer.ts:73-75`) and into the legality checks. The alternative, declaring them in 9.2, was turned down because Story 9.1 cannot type a command request shape without them and would have to forward-declare a tuple its own module does not own.
- **Five shapes carry the four transport channels and all five are HTTP-keyed.** `RequestShape` (`interface.ts:83-90`), `InputBinding` (`src/core/schemas/plan.ts:92-97`), `ObservedCallInputs` (`sealed-run-record.ts:153-158`), `ProbeInputBinding` (`defect-signature.ts:79-84`), and `WitnessInputs` (`sensitivity-witness.ts:17-28`). The settled design named only the first. All five move, split by artifact so each story carries one artifact's bump: Story 9.1 takes `RequestShape` and `InputBinding` and `WitnessInputs` under the eval contract's bump, and Story 9.4 takes `ObservedCallInputs` and `ProbeInputBinding` under the run record's and the probe's.
- **Twenty call sites read an HTTP-shaped field off a resolved `Operation`.** They are enumerated with line numbers in Story 9.3's Code Map. The largest families are the twelve that iterate `TRANSPORT_CHANNELS` against `operation.requestShape[channel]` and the eleven that read `operation.responseDescriptor`. Each is classified in that story as kind-neutral or needing a branch, against the source rather than by assumption.
- **`PlanIndex` drops the interface, which is why no shipped check can be kind-aware today.** `PlanIndex` (`src/core/seal/plan-index.ts:134-138`) exposes `stepOf`, `operationOf(operationId) => Operation | undefined`, and `stepsUsing`, and `Operation` carries no kind. `qualification.ts:129-133` states the consequence in the source: "The contract side cannot decide this: reachability rejects a tailed `stdout` pointer and returns reachable for a bare one unconditionally, because an operation carries no interface kind." The index widens in two moves: Story 9.1 adds `interfaceKindOf` and `declaresOperation` additively, because its own reachability deferral needs them, and Story 9.3 widens `operationOf`'s return type to the union once the twenty call sites that read a resolved operation have been branched.
- **The probe side already has half the rule and the contract side has none.** `condition-text-channel-on-api` (`qualification.ts:62`, fired at `:311-320`) rejects a signature predicate addressing `stdout`, `stderr`, or `exit-code` when `interfaceKind === 'api'`. Its mirror for a command signature addressing a response channel does not exist, and neither direction exists on the contract side at all. Story 9.2 mints the contract-side codes; Story 9.4 adds the probe-side mirror to `QUALIFICATION_FAILURES` (`qualification.ts:49-70`), which is a closed vocabulary separate from AD-5 by that module's own header at `:6-9`.
- **Two total switches over `EvidenceChannelName` are the epic's forcing functions.** `channelRoot` (`evidence-resolution.ts:82-106`) and `projectChannel` (`quotation.ts:64-86`) are exhaustive switches with no default. Adding a channel to `EVIDENCE_CHANNELS` makes both fail the typecheck, so no consumer of the new channel can be forgotten silently.
- **`seal` is not kind-neutral and the settled design did not name it.** `operationReference` (`src/core/seal/derived-reference.ts:60-62`) renders every operation as "the `<words>` endpoint", and `TRANSPORT_ORDER` (`:83-88`) is a hardcoded four-member HTTP list that `bindingEntries` (`:93-105`) iterates, so a command step's bindings render as nothing at all and a command operation is described to the evaluator as an endpoint. Both are Story 9.3's, and the brief's own schema needs no change: `BriefInterface` (`src/core/schemas/sealed-evaluator-brief.ts:34-39`) carries `logicalId` and `kind` only, so it is genuinely kind-neutral and the sealed brief takes no `schemaVersion` bump.
- **AD-13's four checks move together on every schema story.** They are the rejection suite (`tests/schemas/published/published-rejection.test.ts:1`, self-labelled "Check one of four"), the byte-exact drift check (`scripts/check-schemas.ts:1`, `check:schemas`), the differential (`tests/schemas/published/differential.test.ts:1`), and the keyword-mutation check (`tests/schemas/published/keyword-mutation.test.ts:1`). Only the second has its own npm script; the other three ride `test:coverage`, `validate`'s last step. `keyword-mutation.test.ts:6-11` asserts the survivor set equals the computed exempt set, so a new keyword with no fixture that kills it fails the build.
- **The census duplication this epic inherits.** `deferred-work.md`'s first open entry records that the published-schema census numbers are hand-maintained integer literals duplicated across `tests/schemas/constraint-ledger.test.ts`, `publish.test.ts`, `differential.test.ts`, `keyword-mutation.test.ts`, and `published-rejection.test.ts`, and that "every future schema change now has five places to update in lockstep and the risk compounds with each one." This epic is four schema changes. The entry is not closed here; each schema story updates the five files and Story 9.5 verifies the totals once.
- **One test pins the eval contract's version and it is the check the two byte gates cannot be.** `tests/schemas/eval-contract-version.test.ts:51` holds `EVAL_CONTRACT_SCHEMA_VERSION = 3` and asserts every authored literal, every member of `CORPUS_CONTRACTS`, every contract `buildDevCorpus` emits, and the worked example's contract against it. Its own header says why: `check:corpus` and `check:worked-example` "both rebuild through the same literal they compare the commit against, so a wrong stamp and its check agree with each other." Each of the epic's two eval-contract bumps raises that constant first and lets the failures name every literal that has not moved.
- **Adding one corpus contract moves a generated table and six hand-written counts.** `docs/ad31-coverage-predicates.generated.md` is built from `CORPUS_CONTRACTS` and `CORPUS_CELLS` (`tests/coverage/fixtures/corpus.ts:510,362`) through `scripts/generate-ad31-table.ts:16-19`, so `generate:ad31-table` reruns whenever the corpus grows. The count "nineteen" is hand-written prose in six places: `docs/reference/cli-commands.md:285,291,295`, `docs/how-to/author-behavioral-contracts.md:107,114-116`, `docs/explanation/behavioral-evaluation-contracts.md:157`, `docs/index.md:89`, `docs/explanation/roadmap.md:16`, and `scripts/dev-corpus-target.ts:108`, which is the generated `corpus/dev/README.md`'s own source. `check:docs` does not scan `docs/`, so none of the six is gated. All are Story 9.5's.

## Cross-Story Dependencies

- Story 9.2 depends on Story 9.1 for the command channel tuple and for a command operation to root an `artifact` pointer against; there is nothing for a per-kind legality check to read until an operation can be command-shaped.
- Story 9.3 depends on Stories 9.1 and 9.2 for both operands of every check it writes: the declared shape and the addressable channel. It is also the story that removes `cli` from `checkInterfaceKind`'s rejection, so nothing before it can compile a command contract even in a test.
- Story 9.2 mints its codes and ships their throwers in the same diff. A code minted with no thrower is the defect `deferred-work.md:125-128` records AD-16's two forbidden-input checks having had for a whole epic, and the accessor those throwers read is Story 9.1's `interfaceKindOf` rather than Story 9.3's widened `operationOf`, which is why the split lands cleanly.
- Story 9.4 depends on Story 9.2 for the channel names an `Observation` must record and for the `artifact` channel's identifier segment; `ObservedCallInputs` and `Observation` are the two shapes a pointer minted in 9.2 resolves against at score time, and until 9.4 lands, a command pointer parses, compiles, and resolves `absent` at score time. That window is named in Story 9.2's decisions and closed in Story 9.4.
- Story 9.4 is the only story that may retire `qualification.ts:718-726`'s rejection for `cli`, because that rejection's stated reason is that a command signature "would declare a meaningless `POST /path`", and the variant that gives it a real identity is 9.4's own.
- Story 9.5 depends on all four and is the epic's evidence: a command contract in `corpus/dev/` that compiles and seals through the shipped stages, a regenerated published surface, and the disclosure. It is also the only story that may claim the entry criterion in `TEST-PLAN-NEXT-STEPS.md:315-328` is met, and it claims it for the shape rather than for the adjacent repository's document, which lives outside this tree.
- Four artifacts take breaking `schemaVersion` bumps and each is owned by exactly one story: the eval contract 3 → 4 (Story 9.1), the eval contract 4 → 5 (Story 9.2), the sealed run record 3 → 4 (Story 9.4), and the probe 2 → 3 (Story 9.4). The eval contract moves twice because two stories retype it and each must be independently releasable, which is the rule `epic-7-context.md:31` states and the reason the sealed run record moved 1 → 3 across Stories 7.1 and 7.2.
