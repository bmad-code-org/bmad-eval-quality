## Intent

**Problem:** `apiShapedInterface` (`src/core/schemas/interface.ts:281-286`) hands `mcp` the HTTP-shaped `Operation` at `:296`, and four of that shape's declarations are wrong for a tool call. `method` (`:123`) is required over the seven verbs at `:95-103` and a tool call has none. `pathTemplate` (`:124`) is the only place a tool name could go, because every MCP call shares the one transport identity `tools/call`; two tools declared as `POST /tools/call` render one signature through `operationSignature` (`src/core/compile/interface-inventory.ts:59-64`) and collide under `duplicate-operation-signature` (`:107-111`), and the kind ships no convention for a spelling that avoids it. Three of the four request channels at `:85-92` are dead, since a tool call carries arguments and nothing else. And `responseDescriptor` is the shape Story 11.3 settled.

**Approach:** Follow the `CommandOperation` precedent (`interface.ts:230-252`) that Epic 9 set when it chose a second operation shape over bending the HTTP one. `mcp` gets `McpOperation`: a flat tool identity, one `arguments` request channel, Story 11.3's descriptor under a one-member tagged `descriptorChannel`, and the kind-neutral `stateChangeMarker`, `volatilePointers`, and `sensitivityWitness` every operation shape already carries. `AnyOperation` (`:255`) widens to three members, `apiShapedInterface` is left with `web` as its only member and says so in the source, and the three shapes on the eval contract that mirror a request shape (`InputBinding`, `WitnessInputs`, and the witness channel tuple) each take a third branch. Two artifacts take a version bump, because `WitnessInputs` is reached from both: the eval contract through `SensitivityWitnessLeg.inputs` and `FixtureReset.inputs`, and the probe through `ManifestationWitness.inputs` (`src/core/schemas/probe.ts:36`). Nothing opens a gate: `SUPPORTED_INTERFACE_KINDS` (`interface-inventory.ts:31`), `preflight/plan.ts:305`, and the qualification gate at `score/qualification.ts:754-763` all stay closed, so an `mcp` contract parses at the end of this story and still fails compilation, which is the state Story 11.5 closes.

## Decisions settled by construction

**Decision 1: `mcp` needs its own defect-signature branch, AD-40's contract-independence requirement is what forces it, and Story 11.6 lands the whole signature side.**
AD-40 resolves a defect signature by comparing the identity a signature declares against the identity an operation declares, and `resolveHomeOperation` (`qualification.ts:115-135`) performs that comparison through `anyOperationSignature`. After this story an `mcp` operation renders its identity from `toolName`. An `mcp` signature that kept `ApiDefectSignature`'s `method` and `pathTemplate` (`defect-signature.ts:165-166`) would render `POST /tools/call` and compare it against a tool name, so resolution returns `null` for every contract, forever. The requirement AD-40 states is that the identity be contract-independent, and a declaration that binds nothing is inert. So the api-shaped branch is not a workable option, and `mcp` needs its own branch beside the `cli` literal at `:178`, declaring `toolName` as `CommandDefectSignature` declares `invocation`.

The one-branch-over-three-kinds comment at `:151-162` is the argument against splitting, and it does not survive the split. Its reason is byte-identity: "Three would publish three byte-identical subschemas, and AD-13's mutation sweep cannot attribute a keyword deletion to one of several identical branches." An `mcp` branch declaring a tool identity is not byte-identical to an api-shaped one, so the attributability defect that comment protects against cannot arise. `ApiDefectSignature.interfaceKind` narrows to `z.enum(['api', 'web'])` and the union comment at `:183-188` moves from three values to two.

Story 11.6 lands all of it, and the reason is that `defect-signature.ts` is one file answering one question. `ProbeInputBinding` sits at `:86-95` and is consumed at `:109` by `ProbeStepSelector`, so the ninth `arguments` channel a signature's selector needs and the `mcp` signature branch itself are the same file and the same change. Splitting them would land a branch whose selector cannot bind the channel the kind actually has. Story 11.6 therefore takes `McpDefectSignature`, the enum narrowing, the ninth `ProbeInputBinding` key, the qualification gate at `qualification.ts:754-763`, the probe's second bump, and the `UNION_BRANCH_FIXTURES` seed for the signature branch, in one diff. It has to be one diff for the census reason too: `keyword-mutation.test.ts:190-193` fails on any published keyword no fixture flips, so a branch landing without its seed leaves `npm run validate` red.

The interim state this story leaves is coherent. An `mcp` contract parses; an `mcp` probe stays schema-valid, because `ApiDefectSignature` still admits `'mcp'` until 11.6 narrows it; `resolveHomeOperation` returns `null` for it; and the gate at `qualification.ts:754-763` refuses it under `signature-interface-kind-unsupported` exactly as it does today. Story 11.5 opens the compile and pre-flight gates and names the same window; Story 11.6 closes it.

**Decision 2: the tool identity is one flat `toolName`, carrying no server segment and no wrapper object.**
`CommandInvocation` is a wrapper because a command's identity has two parts and AD-40 compares them as segments. An MCP tool call has one: the wire carries `tools/call` with a `name`, and there is no second segment for two implementations to disagree about a separator for. A wrapper around one field would publish an object whose only job is to hold a string.

The server's own identity is left out on the same reasoning. `PermittedInterface.logicalId` names the server, and neither `operationSignature` nor `commandSignature` folds the declaring interface's `logicalId` into the rendered identity. AD-40 needs a signature authored against a corpus to bind a second contract's operation, and a second contract is free to name its server anything; folding in a contract-local logical id would make the identity contract-local, which is the property AD-40 forbids. Downstream consequence: Story 11.6's `McpDefectSignature` declares `toolName` alone. **Corrected during the build:** two `mcp` interfaces declaring the same tool name are not told apart, they collide. Decision 4's key is scoped by shape family and the family is the same for both, so a contract declaring two tool servers that each publish `search` fails compilation with no fix its author can apply, since renaming one breaks the binding to the real server. That is a real limitation of a contract-independent identity and it is pinned by a test rather than left to be discovered. If AD-40 ever needs two servers in one contract the fix is a namespace on the map's key and never on the rendered identity, because the rendered identity is what a signature author reads.

**Decision 3: `ToolName` is its own pattern, and `Identifier` is the option turned down.**
`Identifier` is `[a-z0-9]+(?:-[a-z0-9]+)*` (`primitives.ts:8`), lowercase kebab. MCP tool names in the ecosystem are overwhelmingly `snake_case`, and `search_notes`, `create_note`, and `searchNotes` all fail that pattern. A kind whose transport identity refuses the spelling nearly every real server uses ships unusable, and the author's only recourse is to invent a second name for the tool and lose the binding to the server it describes. So `ToolName` admits ASCII letters, digits, underscore, and hyphen.

Widening `Identifier` itself was the other option and is turned down: it is the type of every operation id, artifact id, principal name, and pointer segment in the tree, its own description records that it excludes `/` and `~` so it can be embedded in a pointer without escaping, and widening it would move every `pattern` in twelve published documents for one field's sake. A tool name is embedded in no pointer, so it needs none of that. AD-35 stays structural because the charset admits no `/`, `:`, or `.`, so a URL, a host, a port, and a filesystem path are each a parse error rather than a compile finding. Downstream consequence: Story 11.6's signature branch reuses `ToolName`, and Story 11.8's dev-corpus exemplar is free to spell its tools the way the ecosystem does.

**Decision 4: `checkDuplicateOperationSignature` keys on the declaring kind beside the rendered identity.**
Today a cross-kind collision is impossible by charset: `commandSignature` joins identifiers with a space and `operationSignature` renders a verb, a space, and a slash-rooted template, so no two can ever render the same string. A bare tool name breaks that accident. An `mcp` tool named `notes` and a `cli` executable named `notes` with an empty `subcommandPath` both render `notes`, and the check at `:100-116` would refuse a contract declaring both.

That refusal would be a false positive. `duplicate-operation-signature` exists so that AD-40's first match is the only match, and `resolveHomeOperation` already compares identities inside their own kind, so a tool and a command sharing a name resolve unambiguously. Two ways to fix it were on the table: prefix the rendered identity with the kind, or key the check's map on the pair. Prefixing loses, because the rendered identity is also what AD-40's message quotes and what a signature author reads, and a prefix would put an internal discriminator into published output. So the map is keyed on the pair, and the collision message names the family alongside the identity and scopes its erasure clause to the family it applies to, since a tool name and an executable path carry no parameters to erase.

**Corrected during the build:** the key is scoped by shape *family* rather than by kind, and `api` and `web` share one because they share an operation shape. Two operations declaring the same method and path template across an `api` interface and a `web` interface therefore still collide, which is right: they render one identity from one shape. `signatureFamilyOf` is a `switch` over `InterfaceKindName` with no default arm, so a fifth kind fails the typecheck at the declaration instead of landing in the api family, which is the same trap Decision 7 removes one level down. Downstream consequence: Story 11.5 inherits a check that already tells the three kinds apart, and Story 11.8's dev-corpus exemplar may name a tool after a command in the same corpus without an unexplained rejection.

**Decision 5: the mcp input channel is `arguments`, a ninth member of `INPUT_CHANNELS`, and reusing `argument` is the option turned down.**
Reuse is genuinely cheaper and is worth stating exactly: `INPUT_CHANNELS` would stay at eight, `INTERACTION_POINTER_PATTERN` would not move, and `ObservedCallInputs` (`sealed-run-record.ts:200-209`) and `ProbeInputBinding` (`defect-signature.ts:86-95`) would each stay at eight keys, which would take a ninth key off Story 11.6 entirely. It is turned down because a channel name is vocabulary, and `argument`'s own description (`interface.ts:177-179`) says what it means: "Positional arguments, keyed by the name the contract gives each position. The key is the author's own label; position is not encoded here, because no AD-31 predicate reads argument order." A tool call's arguments are a named object with no positions at all, so the reuse would require that description to be widened until it says nothing, and `pointer.ts` would own a channel whose meaning depends on a kind the pointer grammar cannot see. `arguments` is the wire spelling MCP itself uses, which is the same reason `subcommandPath` took the spelling the contracts authored outside this repository already used.

The near-miss with `argument` is real and is pinned: a test asserts both are members of `INPUT_CHANNELS`, that they are distinct, and that an `mcp` operation declaring `argument` fails to parse. Access stays by indexing (`requestShape[channel]`, the pattern `requestChannelsOf` at `declared-inputs.ts:117-130` already uses), which is what keeps the name out of a destructuring position where a strict-mode binding named `arguments` would be illegal. Downstream consequence: Story 11.6 adds the ninth key to `ObservedCallInputs` and `ProbeInputBinding` under those two artifacts' own version bumps, and Story 11.8's census sweep counts the widened pointer pattern once.

**Decision 6: `WitnessInputs` gains its mcp branch here, and the probe takes its first breaking bump with it.**
`McpOperation.sensitivityWitness` is required-and-nullable on `Operation:133-135`'s own terms, and AD-10 demands a witness from any operation declaring request keys while exempting one that declares none. An mcp operation that declares an `arguments` key and has no expressible witness leg would have to declare `null` and would then fail `undeclared-mandatory-input`. That state is precisely the defect `sensitivity-witness.ts:151-160` records for `ManifestationWitness`, where the transport spelling left a seeded defect against a command-line system unrepresentable in both directions. Shipping the same defect knowingly for a third kind is not an option, so the branch lands here.

The reach is what makes this two artifacts. All three leg shapes take the union: `SensitivityWitnessLeg.inputs` (`:88`) and `FixtureReset.inputs` sit on the eval contract, which is already taking its 4-to-5 bump in this story, and `ManifestationWitness.inputs` (`:166`) sits on `Defect.manifestationWitness` (`probe.ts:36`), so `schemas/probe.schema.json` regenerates and the probe moves 3 to 4. AD-11's rule is that retyping is breaking, and the union under `inputs` is retyped, so the probe's bump is BREAKING and its record goes in `inputs`' own `.describe()`. Every probe legal before is legal after, and no probe reader narrows, so the version-3 instance in the field still parses. The stamp records the retype, and `src/core/compile/schema-version.ts:21-33` compares the eval contract's stamp alone, so nothing gates the probe's. Story 11.6 takes the probe's second bump, 4 to 5, with `McpDefectSignature` and the ninth `ProbeInputBinding` key. Each story that retypes an artifact takes its own bump, which is the rule Epic 9 set when the eval contract moved 3 to 4 in Story 9.1 and 4 to 5 in Story 9.2, so each is independently releasable. Known-bad state avoided: an operation shape whose mandatory witness field has no legal value.

**Decision 7: the kind resolution becomes three-way at its one site, `isApiOperation` is repaired and kept, and a second boolean beside the first is the option turned down.**
`isApiOperation` is spelled `!isCommandOperation` (`declared-inputs.ts:104-106`) and returns `true` for an mcp operation. Every consumer of the two-arm dispatch inherits that: `descriptorChannelOf` would answer `response-body` from the wrong arm for a kind whose descriptor channel Story 11.3 shaped, `legalChannels` (`compile/sensitivity-witness.ts:314-317`) would answer the api witness channels, `requestChannelsOf` would index the four transport channels against a shape that has one, and `operationReference` (`seal/derived-reference.ts:71-76`) would call a tool an endpoint in text a sealed evaluator reads. None of the four fails a typecheck, and `checkEvidenceReachability` runs ahead of `checkInterfaceKind` in `compile.ts`, so three of them are reachable by an `mcp` contract before the gate that names its real defect ever fires.

Adding `isMcpOperation` beside `isCommandOperation` and leaving `isApiOperation` as a negation was the cheaper edit and is turned down: it leaves the same trap armed for a fifth kind, and the trap is silent by construction, since a boolean negation has no exhaustiveness for a compiler to check. So `isApiOperation` tests its own required field, and every dispatch site becomes a three-way resolution over the operation union.

Deleting `isApiOperation` was the other option, on the ground that `src/` has no caller. It is turned down because two callers outside `src/` do exist and both would break: `tests/coverage/table.test.ts:317` and `tests/preflight/fixtures/observations.ts:355`, each spelled `operationsOf(...).filter(isApiOperation)` to narrow a `PermittedInterface`'s operations to the HTTP-shaped ones. Deleting the predicate would make both files inline the same negation and inherit the wrong answer for `mcp` that this decision exists to remove. Three of the five dispatches gained an `mcp` arm: `descriptorChannelOf`, `requestChannelsOf`, and `inputChannelsOf`. `descriptorArtifactOf` and `declaredArtifactsOf` did not, and their `!isCommandOperation` tests are correct as they stand, because only a command nominates a file: neither an operation that speaks HTTP nor a tool call declares one. The claim to check them against is not that every site grew an arm; it is that no site answers for a tool call through an arm written for another kind.

Downstream consequence: Story 11.13 works its exhaustiveness list against a `declared-inputs` module that already answers for three kinds, and Story 11.5 keeps the predicate rather than dropping it. What a fourth `AnyOperation` member does not do is break the typecheck everywhere: seven of the nine api-arm-as-`else` dispatches across `src/` compile clean and treat it as HTTP-shaped, so a fifth kind still needs the grep this build used.

**Decision 8: this story absorbs the census constants its own two bumps force, and Stories 11.6 and 11.8 sweep the rest.**

## Design Notes

The organising idea is the one Epic 9 already proved: the discriminator exists, and the operation shape is what should depend on it. `cli` got its own shape because a command has no method and no path template. `mcp` has the same problem one level sharper, since every tool call shares one transport identity, so the HTTP shape does not merely waste fields, it makes two correct declarations collide.

The shape, for orientation only:

```ts
export const McpRequestShape = z.strictObject({
	arguments: KeyedShapeDescriptor, // the one channel a tool call has
})

export const McpDescriptorChannel = z.discriminatedUnion('kind', [
	z.strictObject({ kind: z.literal('structured-result') }),
])

export const McpOperation = z.strictObject({
	operationId: Identifier,
	toolName: ToolName, // AD-35: a logical tool name, charset admitting no / : .
	stateChangeMarker: z.boolean(), // AD-20 rule 7 and AD-10 both read it
	requestShape: McpRequestShape,
	descriptorChannel: McpDescriptorChannel, // one member today, additive later
	responseDescriptor: ResponseDescriptor, // Story 11.3's shape, one per operation
	volatilePointers: z.array(DescriptorPointer),
	sensitivityWitness: SensitivityWitness.nullable(),
})
```

`AnyOperation` widens to three members and `operationsOf` (`interface.ts:312-314`) keeps being the one place the widening is spelled, so no call site invents its own.
